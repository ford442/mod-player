# Audio worklet assets

Self-hosted worklet and libopenmpt assets served from `public/worklets/` (copied to `dist/worklets/` on build).

## Production JS worklet path (default)

| File | Role |
|------|------|
| `openmpt-worklet.js` | `AudioWorkletProcessor` — renders module audio in `process()`. **Generated** (`// generated — do not edit` header) from `audio-worklet/js/openmpt-processor.ts` by `npm run build:js-worklet` (esbuild) — edit the TS source, not this file. See `docs/WORKLET_AUDIO_BUG.md` § "Compiled TypeScript worklet source (#435)". |
| `libopenmpt-worklet.js` | Emscripten **glue** for libopenmpt 0.8.9 (classic script, ~50 KB, Closure-compiled). Generated by `npm run build:js-libopenmpt`. |
| `libopenmpt-worklet.wasm` | The **real WebAssembly** binary (~1.4 MB at `-Os`, `\0asm` magic, no SIMD, native wasm exceptions). Same build, same bytes. |
| `libopenmpt-playback.js` / `.wasm` | The AudioWorklet's own heap (#513): the same libopenmpt, exceptions, exports and memory limits, linked with `-sWASM_WORKERS` (**shared** memory, locked malloc, threaded C++ runtime) and the main-thread TLS initializer forced in (below). `npm run build:js-libopenmpt -- --playback`. |

Both pairs are tracked in git (like the JS processor) so deploys need no emsdk. They are built by
`scripts/build-js-libopenmpt.sh` and described by generated manifests
(`audio-worklet/js/libopenmpt-{worklet,playback}.generated.json`: sizes, SRI hashes, a content-hash cache key,
the emsdk that built them, whether the memory is shared). Nothing replaces `globalThis.WebAssembly`:

| Consumer | Pair | How it loads it |
|----------|------|-----------------|
| Main thread | worklet | `<script src=…?v=…>` injected into `index.html` by `vite-plugins/libopenmptHtml.ts` (SRI-pinned; `Module.locateFile` versions the `.wasm` too) |
| Parser worker | worklet | `new Function(glue)` + `locateFile` → the same `.wasm` (`utils/libopenmptAssets.ts`) |
| AudioWorklet, crossOriginIsolated page | **playback** | main thread `fetch`es both, validates them (`utils/workletLibAssets.ts`), posts `initLib {scriptText, wasmBytes}` |
| Create worker (`workers/openmpt-create.worker.ts`) | **playback** | joins the worklet's `WebAssembly.Memory` as a wasm worker (below) |
| AudioWorklet, not isolated (or `?audioCreate=worklet`) | worklet | as above; modules are then created inside the worklet |

The main-thread / parser-worker wasm must stay **non-threaded**: `verify:js-libopenmpt` reads the memory import out
of each binary and fails if the shared pair's memory is shared (or the playback pair's is not).

### Module create off the audio thread (#513)

`openmpt_module_create_from_memory2` on a large file takes tens of ms (a 16 MiB, 64-channel IT: ~20–90 ms), and
inside the worklet it runs on the audio thread, so whatever was playing stalls. With the playback heap:

1. After `initLib`, the worklet allocates a 1 MiB stack + TLS block in its heap and posts `createHeap {memory, stackLow, stackSize}`.
2. The main thread (`hooks/audioGraph/createWorkerHost.ts`) starts one create worker per heap: it evaluates the playback
   glue with `Module.$ww`, that memory, and that stack (Emscripten skips the static constructors and runs
   `emscripten_wasm_worker_initialize`). The node gets a `MessagePort` to it (`attachCreatePort`).
3. `load` now goes to the worker (`postModuleLoad`). It mallocs and copies the file, creates the module — heap growth
   happens here, never on the audio thread — and posts `staged {modulePtr}` to the worklet.
4. The worklet keeps rendering the old module, fades it out over 10 ms, swaps the pointer in `process()`, posts `loaded`,
   and sends the old module back (`destroy`). `process()` never creates, destroys or mallocs.

A pointer has one owner at a time (worker → worklet on `staged`, worklet → worker on `destroy`); a newer `staged`
supersedes one still waiting for its fade, and the superseded one goes back. A failed create comes back as the same
`error` an in-worklet load posts. The first load of a session races the handshake and is created in the worklet;
nothing is playing yet. If the worker fails, its pending loads are re-sent to the worklet.
`tests/createThread.integration.test.ts` runs this pipeline in Node (compiled processor, real worker, real heap);
`npm run smoke:create-thread` measures it in Chromium against `?audioCreate=worklet`.

Every request carries `?v=<content hash>` so a browser/service-worker cache can never pair a new glue with an old
`.wasm` (their import tables are minified per build).

### Load sequence (worklet)

1. Main thread: `audioWorklet.addModule(…/openmpt-worklet.js?v=N)` (`hooks/useWorkletLoader.ts`; `?v=` is a content hash of the compiled processor, from `audio-worklet/js/worklet-version.generated.json` — no manual bump needed).
2. Main thread creates `AudioWorkletNode` with processor name `openmpt-processor`.
3. Main thread fetches the pair's `.js` **and** `.wasm` in parallel — `libopenmpt-playback.*` on a crossOriginIsolated page, else `libopenmpt-worklet.*` — and rejects anything wrong *here* (HTML 404 body, missing `\0asm` magic, a stale wasm2js glue).
4. Main thread `postMessage({ type: 'initLib', scriptText, wasmBytes }, [wasmBytes])`, then `setRenderParam` (interpolation) and `load` (the first load goes to the worklet; later ones to the create worker once it is up — see above).
5. Worklet evaluates the glue via `new Function` (classic-script scope), seeded with `Module.wasmBinary` (the worklet scope has no `fetch()`), **waits for `onRuntimeInitialized`** (`audio-worklet/libRuntimeReady.ts` — never infer readiness from `_openmpt_*` being defined: newer emsdk defines lazy stubs at eval time), then accepts `load` / `play` / `seek`.

There is **no** wasm2js path: `initLib` without `wasmBytes` is rejected. `npm run verify:wasm` / `verify:js-libopenmpt` fail on HTML-as-wasm and on a wasm2js glue.

### Rebuilding the pair

```bash
source /path/to/emsdk/emsdk_env.sh      # emsdk 3.1.51 — the pin; another emcc is an error (XASM_ALLOW_EMSDK_DRIFT=1 overrides)
npm run build:js-libopenmpt             # → libopenmpt-worklet.{js,wasm} + manifest
npm run build:js-libopenmpt -- --playback   # → libopenmpt-playback.{js,wasm} + manifest
npm run verify:js-libopenmpt            # static + feature checks of both pairs; --smoke also boots + renders them
```

Where things are decided:

- `scripts/lib/libopenmpt-source.sh`: libopenmpt's version (**0.8.9**) and the sha256 of its tarball. A download that does
  not match is refused. 0.8.5–0.8.9 fixed a heap out-of-bounds write in the SymMOD loader (WAV IMA ADPCM samples), an
  out-of-bounds read in MPTM custom tunings and one in reverse playback past a loop; this app parses untrusted uploads.
- `scripts/lib/wasm-flags.sh`: the emsdk pin and the audited flags.
  - **Wasm exceptions** (`-fwasm-exceptions`, compile and link). A corrupt upload must return `NULL`, not abort the
    shared worklet runtime.
  - `-mbulk-memory -mnontrapping-fptoint`. LLVM 17 enables neither by default. With them, trapping float→int
    conversions drop from 273 to 14 and memcpy/memset become `memory.copy`/`memory.fill`.
  - `-fvisibility=hidden` and pinned `-std=`, which libopenmpt's own makefile would add.
- `scripts/build-js-libopenmpt.sh`: the rest of the build.
  - `-Os` and Closure on the release glue (both in `wasm-flags.sh`): the pairs are ~1.38 MB of wasm and ~50 KB of
    glue each, against 1.74 MB / 104 KB at `-O3` without Closure, at the same render cost and bit-identical PCM
    (`docs/WORKLET_AUDIO_BUG.md` § "One toolchain").
  - **No SIMD**.
  - `INITIAL_MEMORY=32 MiB` with growth (the wasm2js glue reserved ~512 MiB).
  - The whole libopenmpt C API exported, and `stringToUTF8` deliberately **not** exported (the app's polyfill has a
    different signature).
  - Each variant builds in its own tree under `vendor/…-jsengine-<variant>-emsdk<ver>`.
- `scripts/verify-wasm-features.mjs`: decodes every instruction of both binaries and checks the result. Required:
  try/catch, saturating float→int, bulk memory. Forbidden: SIMD. Atomics are required in the playback pair and
  forbidden in the shared one.

**Main-thread TLS in the playback heap.** With `-sWASM_WORKERS`, the heap main thread's TLS block is set up by
`emscripten_wasm_worker_main_thread_initialize`, a `constructor(48)` in `libwasm_workers.a`. Here that thread is the
AudioWorklet. emsdk 3.1.51 links that archive normally, so the constructor's member is only pulled in when something
references it, and nothing here does. The constructor never ran, and TLS accesses kept their raw offsets (addresses
near 0, at the far end of the stack).

Wasm EH keeps its catch selector in a thread-local (libunwind's `__wasm_lpad_context`), so every typed C++ catch on the
worklet fell through to `catch (...)`. libopenmpt then rejected recoverable files as "unknown internal error": a
truncated IT 2.15 sample block, which it normally catches as `BitReader::eof`, is one example. That hit every
in-worklet create: the first load of a session and any load after the create worker dies. The create worker is a wasm
worker, initialised by `emscripten_wasm_worker_initialize`, and was never affected.

Later emsdk whole-archives `libwasm_workers` for exactly this reason; the playback link sets
`EMCC_FORCE_STDLIBS=libwasm_workers` to do the same. (`-Wl,--undefined=…` pulls the member in but does not get the
constructor called in a `-O0` link; a hand-written `__wasm_init_tls` constructor worked only when the TLS layout
happened to cooperate.) `verify:js-libopenmpt` loads that truncated IT on every thread (worklet scope, heap main thread,
create worker) and fails without the fix.

**Debug builds and symbol maps.** `--debug` (`-O0 -g -sASSERTIONS=2`) adds `worker,shell` to `-sENVIRONMENT`. An
ASSERTIONS glue checks its environment at load time, and with `web` alone it threw "not compiled for this environment"
inside an AudioWorkletGlobalScope, which has no `window` or `importScripts`. To check that a debug build boots where
the app runs it: `OUT_DIR=/tmp/dbg npm run build:js-libopenmpt -- --debug`, then
`node scripts/verify-js-libopenmpt.mjs --boot /tmp/dbg/libopenmpt-worklet.js`; CI does this for both pairs. Release
builds write `vendor/symbol-maps/<pair>.<cache key>.symbols`, the function index → name map. The cache key is the
`?v=` the app loads, so a `wasm-function[N]` frame from production can be decoded; CI uploads the maps as the
`libopenmpt-symbol-maps` artifact.

**SIMD is rejected, not an untested production mode:** `--simd` (`-msimd128`) was rebuilt and benched against the shipped
wasm on 2026-10-25 (emsdk 3.1.51, `npm run bench:js-libopenmpt`, 4-channel MOD and a 64-channel IT, cubic and sinc-8,
three interleaved 30 s runs each): CPU per quantum stayed within run-to-run noise (median −1.5 % to +14.5 %, both signs),
zero over-budget quanta either way, for a 7.6 % larger wasm — so it is not shipped and only one wasm per pair is committed.

### Interpolation

The JS worklet defaults to **Sinc+LP (8)**: with real wasm it costs a few percent of the 128-frame quantum budget even
at 64 channels (the wasm2js glue could only afford cubic). Opt down with `?interp=4` (or
`localStorage.xasm1_js_interp=4`) on weak devices; valid values are 1, 2, 4, 8. The choice is kept across module reloads.

## Engine

The JS worklet is the only engine; when AudioWorklet or its WASM init fails, the app falls back to a main-thread
`ScriptProcessorNode`. The optional native C++ worklet (`openmpt-native.*`, `?engine=native`) was retired — see
`docs/ADR-native-engine.md`.

**No WebAssembly snapshot:** the main-thread libopenmpt is the same real-WASM build as the worklet's, so it never replaces `globalThis.WebAssembly`. (`index.html` used to snapshot the real API as `window.__NATIVE_WEBASSEMBLY__` because the old wasm2js `libmpt/libopenmptjs.js` swapped in a stub whose `Memory()` was never shared — that whole workaround is gone.)

**projectM PCM chunks** are posted by the JS worklet (`projectm-pcm`) → `broadcastPcmBlock`.

**Performance capture (MediaRecorder)** taps the one shared `AudioContext` (`utils/audioContextFactory.ts`). See `docs/EXPORT.md`.

## CI / hygiene

```bash
npm run verify:wasm          # every *.wasm under public/ and dist/ must have \0asm magic (and libopenmpt-worklet.wasm must exist)
npm run verify:js-libopenmpt # both real-WASM pairs: files, exports, manifest, memory (non-shared / shared), instruction-level features,
                             # boots + renders + survives corrupt input + recovers a truncated IT, also through the compiled processor
```

- **Every PR:** `npm run preflight` (`lint-and-build`), shellcheck of the build script + JS-processor guard (`ci.yml` → `build-scripts`), JS `playhead-smoke`.
- **Path-filtered PR / push:** `js-libopenmpt-rebuild` rebuilds both pairs with emsdk 3.1.51 when its inputs change, fails if the committed files drift from a fresh build, uploads the symbol maps, and boots both `--debug` builds in a fake worklet scope.

Never commit failed download bodies (404 HTML) as `.wasm`.
